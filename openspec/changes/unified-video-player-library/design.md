## 背景

当前仓库是一个较新的 Flutter 工程，尚未存在已有 OpenSpec 能力。用户要做的不是单个播放器页面，而是一个面向外部使用的聚合式影视播放器库，需要覆盖 Android、iOS、Windows、macOS。

外部参考项目给出了两个关键方向：

- NipaPlay-Reload 展示了产品级多内核播放器策略，包括 Erika 自研 Rust 渲染内核，以及 Media Kit/libmpv、FVP/libmdk、Flutter 视频组件等集成方式。
- GSYVideoPlayer 展示了影视播放器常见交互：进度条、上一集/下一集、播放/暂停、全屏、切换播放内容或播放器、缩放模式和倍速选择。

这个库必须隐藏后端差异，但不能假装所有后端能力完全一致。有些内核平台覆盖广但原生依赖较重；有些内核更轻，但在 Windows、高级字幕、音轨、渲染控制等能力上存在限制。因此设计上需要显式的能力模型和确定性的降级规则。

## 目标 / 非目标

**目标：**

- 提供一套稳定 Dart API，用于播放控制、状态观察、媒体加载、选集导航、全屏、缩放、倍速、音轨、字幕、错误和生命周期管理。
- 通过可插拔内核支持 Android、iOS、Windows、macOS。
- 在目标平台可支持的前提下，提供 Media Kit/libmpv、FVP/libmdk、官方 Video Player 和 Erika/Rust Renderer 适配器。
- 将 Erika/Rust Renderer 作为一等适配器接入，直接封装 `erika_flutter` 的 `ErikaPlayer`、事件流和原生视频视图。
- 提供一套参考 GSYVideoPlayer 控件习惯的默认影视播放器组件。
- 允许应用显式选择偏好内核，也允许库自动选择和降级。
- 让较重的原生依赖保持可选，避免消费者被迫打包所有内核。

**非目标：**

- 不重新实现 libmpv、libmdk、AVPlayer、MediaCodec、Metal、D3D11、WGPU 或 Vulkan 的播放内核。
- 不承诺所有内核具备完全一致的编解码能力。
- 不构建完整流媒体平台、片单后端、DRM 授权服务或剧集元数据服务。
- 不直接复制 GSYVideoPlayer 的 Android 代码或 Android 专属 API。
- 初始版本不强行实现自研 Rust 渲染内核，除非其适配前置条件已经明确。

## 技术决策

### 决策 1：拆分为核心库和可选适配器

创建一个轻量核心包，负责公开 API、状态模型、默认 UI 和适配器接口。具体内核集成放在独立适配器包或可选模块中：

- `flutter_video_core`：控制器、播放源模型、状态、UI、注册表抽象。
- `flutter_video_media_kit`：Media Kit/libmpv 适配器。
- `flutter_video_fvp`：FVP/libmdk 适配器。
- `flutter_video_platform`：官方 Video Player 适配器。
- `flutter_video_erika`：Erika/Rust Renderer 适配器。

理由：媒体后端通常包含原生二进制、平台配置和传递依赖。可选适配器可以避免每个应用都被迫引入所有播放内核。

备选方案：

- 单包包含所有内核：导入更简单，但会造成依赖膨胀，并且当某个后端在某个平台不可用时更容易引发打包失败。
- 只做应用内集成：实现最快，但无法满足“对外统一 API 聚合库”的目标。

### 决策 2：使用能力驱动的内核选择

每个适配器暴露 `VideoKernelDescriptor`，描述平台支持、播放源类型、渲染模式、字幕能力、音轨能力、倍速范围、缩放模式支持和已知限制。控制器接受 `KernelPreference`，按以下顺序解析实际内核：

1. 调用方指定的精确内核，且该内核兼容当前请求。
2. 调用方指定的有序偏好列表。
3. 当前平台的库默认优先级。
4. 任意已注册且兼容的内核。
5. 如果没有匹配项，返回确定性的“不支持内核”错误。

理由：跨平台媒体能力天然不均衡。能力描述让内核选择可以解释、可以测试，也方便业务方诊断问题。

备选方案：

- 只按平台做编译期 `if`：无法覆盖播放源类型、字幕需求和业务偏好。
- 永远优先某一个内核：实现简单，但违背聚合播放器目标，也会让降级行为变得不透明。

### 决策 3：定义统一播放器状态模型

所有适配器都把原生/后端状态映射到不可变的 `UnifiedVideoState`：

- 生命周期：空闲、打开中、就绪、播放中、暂停、缓冲、结束、失败、已释放。
- 时间线：当前位置、总时长、已缓冲区间。
- 媒体：当前播放源、元数据、已选音轨/字幕/视频轨。
- 呈现：全屏、缩放模式、播放倍速、画面宽高比、可用时的旋转信息。
- 诊断：当前内核 id、后端错误、降级历史、能力快照。

理由：UI 组件和应用业务代码需要稳定状态，而不是按后端分别处理。

备选方案：

- 暴露后端原始状态流：细节更多，但会迫使业务方按内核分支。
- 只保留最低共同状态：更简单，但会丢失影视播放器必需能力。

### 决策 4：默认播放器 UI 只依赖公开控制器

默认 UI 由以下部分组成：

- 视频画面区域。
- 中央播放/暂停按钮。
- 底部控制栏：进度、当前时间/总时长、上一集、下一集、全屏。
- 菜单控制：切换内容或内核入口、缩放模式、倍速档位。
- 覆盖层状态：加载中、缓冲中、错误重试、播放结束。

默认 UI 不能直接调用适配器私有 API，只能使用公开控制器和状态流。

理由：这既能保证 UI 可复用，也能验证公开 API 足够支撑真实影视播放器场景。

备选方案：

- 只提供控制器，不提供 UI：范围更小，但不满足用户要求的 GSYVideoPlayer 风格播放器 UI。
- 为每个后端提供独立 UI：适配器实现更容易，但会割裂 API。

### 决策 5：全屏、缩放和倍速作为统一命令

缩放模式固定为 `original`、`ratio16x9`、`ratio4x3`、`contain`、`cover`、`fill`。倍速档位固定为 `0.5`、`0.75`、`1.0`、`1.25`、`1.5`、`1.75`、`2.0`、`3.0`。如果某个后端不支持请求的命令，控制器返回“不支持能力”错误，不静默改成其他值。

理由：这些控件属于明确需求，必须行为可预测。

备选方案：

- 使用任意倍速和任意缩放值：更灵活，但跨内核行为更难测试。
- 静默裁剪或替换值：看似方便，但容易产生意外行为，调试成本高。

### 决策 6：示例应用以真实播放场景驱动验证

示例应用内置 `defaultPlaybackScenarios`，覆盖：

- MP4 点播：验证普通网络视频、播放暂停、进度拖动、缩放和倍速。
- 短 MP4 切集：验证上一集、下一集和切换内容。
- HLS 点播：验证 m3u8 清单、缓冲、seek 和恢复播放。
- HLS 直播测试流：验证无固定总时长时的进度条和缓冲边界。
- DASH 点播：优先交给 Media Kit/libmpv 或 FVP/libmdk，验证非支持内核的失败提示。
- 错误地址：验证 failed 状态、错误提示和重试入口。

理由：播放器库如果只提供 API 和占位地址，无法证明 UI 和内核选择能覆盖真实影视播放场景。场景清单也能作为业务接入方的 smoke test 模板。

### 决策 7：GSY 风格交互场景落在 demo，通用数据结构落在库层

demo 需要覆盖 GSYVideoPlayer 常见验证项：

- 打开单个播放：旋转、镜像、填充/裁剪。
- 列表/详情：列表切源、动画进入详情、旋转、小窗体。
- 弹幕：作为播放器覆盖层实现，不侵入播放内核。
- 滤镜和 GL 动画：通过 Flutter `ColorFiltered` 与 3D transform 验证渲染外层效果。
- 背景铺满模糊播放：背景封面铺满模糊，前景播放器可交互。
- 进度条小窗口预览：库层提供 `GSYVideoPreviewVttParser`、`GSYVideoPreviewProvider`、`GSYVideoPreviewFrame`，demo 只消费 WebVTT 结果，不对原视频做客户端批量抽帧。

理由：旋转、镜像、弹幕、滤镜、小窗等属于播放器 UI/展示层组合能力，放在 demo 可以验证统一控制器是否足够支撑复杂业务场景；WebVTT 缩略图解析属于可复用数据能力，应放在库层并单测。

## 风险 / 取舍

- 原生依赖体积和打包复杂度较高 -> 保持适配器可选，并分别记录各平台配置步骤。
- 不同后端能力不一致 -> 使用能力描述和显式“不支持能力”错误。
- 自动降级可能掩盖偏好内核的缺陷 -> 在状态中记录降级历史，并暴露诊断信息。
- 全屏在移动端和桌面端差异很大 -> 将全屏实现为平台服务，但控制器语义保持一致。
- 多个后端可能竞争纹理或原生资源 -> 严格控制控制器释放逻辑，并测试切换内核和切换播放源。
- Erika/Rust 原生依赖和工具链要求较高 -> 真实适配器直接使用 `erika_flutter`，并在 descriptor、README 和构建验证中明确 Rust/平台工具链要求；如果某个平台缺少 Erika native library，应返回可诊断的打开失败，而不是悄悄伪装成其他内核。
- UI 范围容易膨胀 -> 默认 UI 只覆盖本次明确要求的影视播放器控件，并通过插槽/构建器开放自定义。
- 网络播放在平台沙盒内可能被权限拦截 -> Android 主 manifest 声明 `INTERNET`，macOS debug/release entitlements 声明 `network.client`。
- 首选内核运行时打开失败可能导致整体不可播放 -> ordered 偏好支持运行时降级；demo 限定只在真实内核之间降级，默认先用官方 Video Player 验证本地 asset/MP4，再降级到 FVP 和 Media Kit，避免 Fake 测试内核掩盖真实失败。
- 远程示例地址可能 403 或被网络环境拦截 -> demo 首屏使用本地 MP4 自检资产，远程 MP4 使用当前可访问的 W3C HTTPS 地址。
- 后端播放后状态不主动变化会导致 UI 进度不动 -> 控制器定时调用适配器 `snapshot`，把进度、时长、缓冲和生命周期持续写回统一状态。
- Media Kit 等后端刚打开时 seek 可能被忽略 -> 打开时通过 `Media.start` 传入起播点，并在控制器切换内核后重试恢复进度。

## 迁移计划

1. 将当前较新的 Flutter 应用结构改为以库为主的结构，并保留示例应用。
2. 先实现核心 API 和用于测试的假内存适配器，再接入真实原生后端。
3. 一次接入一个生产适配器，优先验证 Android、iOS、Windows、macOS 覆盖最完整的后端。
4. 在控制器状态契约有测试覆盖后，再实现默认播放器 UI。
5. 分别记录各适配器安装方式和平台配置，让消费者按需启用。

回滚策略：这是新增能力，回滚时可以移除新增包/文件并回退依赖变更。适配器应分任务、分提交落地，这样某个后端出问题时可以单独回退，不影响核心 API。

## 待确认问题

- 仓库是否要直接改成多包 monorepo，还是先在单包内稳定 API 后再拆分适配器包？
- 各平台默认内核最终应选择 Media Kit/libmpv、FVP/libmdk、官方 Video Player，还是其他内核，需要经过 POC 验证后确定。
- 首个版本是否需要 DRM，还是只把 DRM 作为未来扩展点。
- HLS/DASH 的基础打开和 UI 边界处理属于首版范围；高级轨道选择、外挂字幕加载和 DRM 作为后续扩展。
- “切换播放器内容按钮”首版按切换播放源/剧集处理；切换内核单独提供菜单入口。
